# 02 · 人设（Persona）能力

> 阶段：task-2「设计与独立模块骨架」。本阶段只新增独立文件，不修改任何共享 wiring。
> 接入主链路（host RPC、设置页、微信/QQ 入站注入）是 task-3，依赖渠道裁剪（task-1）完成后执行。
> 相关文档：`docs/上下文增强.md` / `docs/context-enhancement.md`、`docs/adr/0001-semantic-core-native-channel-adapters.md`。

## 0. 一句话结论

个人版为**每个机器人**保存一份「人设」（角色名、性格与语气、补充要求），在**每条进入 Harness 的用户消息**正文前注入 `<dsh_im_persona>{"…"}</dsh_im_persona>` 前缀块，复用上下文增强已经在用的「入站消息前缀 → Host `agent/pre-step` 拆分」链路：

- 人设是**用户消息内容**，不是 Harness 的系统提示词；它不能改变权限、工具、模型、Agent Preset 或工作区。
- 具体做法是把人设块拼在用户正文之前，Host 的 `agent/pre-step` 把它拆成独立的 plugin `instructions` 上下文消息，用户消息本身保持用户输入的原文。
- 人设按 `botId` 存储在 `<DSH_HOME>/integrations/dsh-im/personas.json`，微信与 QQ 共用一份文档、各自独立记录。
- 命令、审批回答、提问回答**不注入**；`/steer` 的补充指令**注入**；`/new` 后**保留**人设；v1 **不提供** `/persona` 切换命令。
- 后续可升级为「动态系统提示词上下文」注入（与现有 `dsh-im:source-guidance` 同一机制），升级路径见 §4.8。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 人设（Persona） | 一个机器人对外的固定角色设定：角色名、性格与语气、补充要求（含禁忌/示例对话/输出规范） |
| 人设块 | 注入用的 XML 标签块 `<dsh_im_persona>…</dsh_im_persona>`，正文是 JSON |
| 注入快照 | 一次 prompt 组装时从 store 同步读到的、已归一化的人设配置 |
| 人设上下文行 | Host 在 `agent/pre-step` 把人设块拆出的独立 plugin `instructions` 消息 |
| 场景（scope） | 群聊 / 私聊。v1 人设**不分场景**，一个机器人一份（见 §3.5） |

## 3. 数据模型

### 3.1 字段

| 字段 | 类型 | 上限 | 默认值 | 是否进入注入块 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `enabled` | boolean | — | `false` | 否 | 总开关。关闭时不拼装任何内容、零额外开销 |
| `name` | string | 40 字符 | `''` | 非空时进入 | 角色名。进入人设块，模型据此自称；**不是**机器人别名（见 §8.1） |
| `tone` | string | 240 字符 | `''` | 非空时进入 | 性格与语气：说话方式、情绪基调 |
| `instructions` | string | 2000 字符 | `''` | 非空时进入 | 补充要求：禁忌、示例对话、输出规范等 |

约定：

- 对象必须**恰好**包含这四个字段（保存路径 `validatePersona` 严格校验）；读取路径 `normalizePersona` 宽容降级为默认值。
- 文本先做换行归一（`\r\n`、裸 `\r` → `\n`）、控制字符与双向控制符剔除、首尾 trim；`name`/`tone`/`instructions` 各自上限按原始字符串长度判定，超限直接拒绝而不静默截断。
- `enabled: true` 但三项内容全空时**等价于未启用**：`personaIsActive` 为 false，不注入。UI 会给出提示（§8.2）。
- 上限取舍：`instructions` 取 2000（小于上下文增强增强提示词的 8000），因为人设块会随每条入站消息进入会话上下文行，重复 token 成本比一次性 guidance 更高（§4.7）。

### 3.2 默认值与规范化优先级

```
DEFAULT_PERSONA = { enabled: false, name: '', tone: '', instructions: '' }   // 冻结
```

- **保存**：`bot.persona.set` → `validPersonaPayload`（结构）→ `validatePersona`（严格）→ 失败返回 `bad-request`，不触达磁盘。
- **读取**：store 加载 → `normalizePersona`（永不抛错）；文件/记录损坏只让对应机器人回落默认值，机器人与其它机器人不受影响。

### 3.3 存储位置与文档结构

沿用现有 dshHome 布局，**不新建数据目录名**（个人版暂不改数据目录，兼容旧数据与品牌无关）：

```
<DSH_HOME>/integrations/dsh-im/personas.json        # 每机器人 v2 选择（库 id / 内联）
<DSH_HOME>/integrations/dsh-im/persona-library.json # 人设库（builtin + 导入项）
```

`DSH_HOME` 解析顺序与 `image-input-settings-store.mjs` 一致：`config.dshHome` → `process.env.DSH_HOME` → `~/.dsh`。

文档结构（version 1）：

```json
{
  "version": 1,
  "personas": {
    "wx_0123456789abcdef01234567": {
      "enabled": true,
      "name": "小助手",
      "tone": "温和、耐心、简洁",
      "instructions": "禁忌：不要编造事实。\n示例：……"
    },
    "qq_fedcba9876543210fedcba98": { "enabled": false, "name": "", "tone": "", "instructions": "" }
  }
}
```

- key 是 botId（`^[A-Za-z0-9_-]{1,128}$`），微信为 `wx_…`、QQ 为 `qq_…`，全局唯一，因此两种渠道可以共用一份文件而互不覆盖。
- 序列化时按 botId 排序，文件内容稳定、便于 diff 与人工修复。
- **写入**：目录 `0700`、文件 `0600`；`mkdir` → 临时文件（`<uuid>.tmp`，`flag: 'wx'`）→ `rename` 原子替换；rename 成功之后才发布内存快照，失败时读者继续拿到上一次已提交值。同一 store 实例的写入串行化。
- **读取**：文件缺失静默当空文档；非法 JSON、版本不符、结构损坏 → 以空文档运行并保留原文件（**加载不重写**），下次显式保存时才重写；单条记录损坏只回落该条；非法 botId 键丢弃。
- **删除机器人**：task-3 在渠道删除流程成功后调用 `clearPersona(botId)`（失败只告警，不阻塞删除）。
- 单例：`getPersonaStore(config)` 按文件路径缓存实例；Host RPC 与渠道注入共用同一实例，保存后下一次入站注入立即生效。
- 渠道启动时必须 `await store.ensureLoaded()`，之后注入路径才能同步 `personaFor(botId)`。

### 3.4 为什么独立存储，而不是塞进 `workspaces.json`

`BotWorkspaceStore` 的 `#persist(...)` 是**位置参数签名**（每加一个配置段就改签名并波及大量调用点）且 `CURRENT_DOCUMENT_VERSION` 迁移需要与裁剪任务协调。人设独立成文件的好处：

1. 零共享文件改动（本阶段硬约束），task-3 只需在渠道 production 里接线；
2. 故障隔离：人设文件损坏不会影响工作区/会话绑定/投递等关键数据；
3. 语义独立：人设是「每机器人内容配置」，与工作区绑定、会话映射的生命周期不同；
4. 未来若要迁入 `workspaces.json`（统一备份/导出），`persona-store.mjs` 的读写接口可以保留，只换底层实现。

### 3.5 场景范围：统一，不分 group/direct

上下文增强分群聊/私聊两个作用域，人设**刻意不分**：

- 目标表述是「使该机器人的所有会话表现一致人设」——同一个人设就是一致性本身；个人版是单一 owner 的机器人，没有多租户诉求。
- QQ 同时有群聊与私聊，群聊里其它成员只应感知同一个角色，不应出现「群里一个性格、私聊另一个性格」的割裂。
- 不同场景的说话风格差异更适合写在 `instructions` 里（开启上下文增强并选择 `conversationType` 字段时模型能读到它，也可用增强提示词按场景补充），而不是维护两份人设。
- 扩展路径：`personas.json` 有 `version` 字段；未来若要分场景，可把记录扩成 `{ default: {…}, group?: {…}, direct?: {…} }` 并升 version，读取端按版本迁移，UI 加场景页签即可，不影响 v1 数据。

### 3.6 迁移

- 基线没有旧人设数据，**无手工迁移**：首次 `get`/启动读到 ENOENT 即空文档，不落盘；第一次保存才创建文件。
- 文档 `version: 1`；未来升版时在 `persona-store.mjs` 的 `normalizeDocument` 内做只读兼容，加载不改写文件（与现有 store 约定一致）。
- v1 不读取也不写 `bot-workspace-store`，因此 bot-workspace 的文档版本升级与本功能互不影响。

### 3.7 渠道接口契约（v2 人设库零返工的关键）

渠道侧（微信/QQ bridge）**不读取人设配置字段，也不知道人设库/存储结构**，只依赖共享模块解析出的「已解析人设」：

```js
// host production 注入给渠道的 provider（task-4 只替换这一处解析器）
persona: { botId, getPersona: () => resolvePersonaInjection(source) }
// → { enabled: true, name: '大肥鱼', text: '最终注入正文' } 或 null

// 渠道侧唯一用法（weixin/qq bridge 相同）
const persona = capturePersona(this.#persona);
if (persona) {
  content = injectPersonaContent(content ?? text, persona);
  contextEnhanced = true;
}
```

- `capturePersona` / `injectPersonaContent` / 块格式 / 标签转义全部在 `src/channels/shared/persona.mjs`；
- v1 四字段配置由 `resolvePersonaInjection` 兼容解析成同一形状，v2 人设库条目直接提供 `text` 原文；
- task-4 改 store / 人设库 / RPC / client 时，渠道接线（provider 之后的代码）零改动；生产侧只需把 `getPersona` 的解析器换成「人设库感知」的版本（或由宿主传入已解析结果）。

### 3.8 人设库与每机器人 v2 选择（task-4）

**人设库**（`src/channels/shared/persona-library.mjs`）：

- 持久化 `<DSH_HOME>/integrations/dsh-im/persona-library.json`，与 personas.json 分离：库是复用素材，personas.json 只保存每个机器人选了谁；
- 条目来源三种：
  - `builtin`：内置「大肥鱼」（正文/简介原样取自参考实现 dsh-persona-dafeiyu，MIT；常量在 `persona-presets.mjs`），**不可删除、不可重命名**；
  - `config`（可选）：插件 config `personaFile` 指向的绝对路径文件，只读；文件缺失/相对路径/不可读时 fail-soft 忽略（只告警）；
  - `imported`：设置页导入（粘贴正文或本地 `.md/.markdown/.txt` 由浏览器 FileReader 读取），名字 ≤60、正文 ≤64,000 字符、最多 200 条；
- 原子写与 personas.json 一致（临时文件 + rename、目录 0700/文件 0600）；损坏文件/单条损坏 fail-soft 且加载不重写；
- `list()` 只返回元数据（id/name/description/source/readonly），正文通过 `get(id)` 按需拉取，避免设置页一次拉取所有长文；
- config 条目 id 固定为 `config`，名称取文件名（去扩展名）。

**每机器人 v2 配置**（`persona.mjs` 的 `validatePersonaConfig` / `normalizePersonaConfig`）：

```json
{ "enabled": true, "source": "library", "personaId": "dafeiyu", "name": "", "tone": "", "instructions": "" }
```

- `source: 'library'`：`personaId` 指向人设库（builtin/config/imported）；`source: 'inline'`：使用本机器人的 name/tone/instructions；
- v1 四字段 personas.json 读取时自动迁移为 `{ source: 'inline', personaId: '' }`，不丢数据、不立即重写文件；
- 注入解析：`resolvePersonaInjection(config, library)` → `{ enabled, name, text }`；library 取条目原文，inline 按 v1 固定格式拼装；库条目不存在/未加载 → null（fail-soft，不注入而不是报错）；
- RPC 保存时校验：库来源必须能解析到条目；内联来源启用时至少有一项内容。

**RPC**（`plugin-src/host/persona-rpc.mjs`，仍走既有管理通道 `/api/dsh-im/persona` 与 rpcAuthority 鉴权）：

| method | 载荷 | 返回 |
| --- | --- | --- |
| `bot.persona.get` | `{ botId }` | `{ persona }`（v2 配置） |
| `bot.persona.set` | `{ botId, persona }` | `{ persona }`（规范化后的 v2 配置） |
| `persona.library.list` | `{}` | `{ entries: 元数据[] }` |
| `persona.library.get` | `{ id }` | `{ entry: { id, name, text, source, readonly } }` |
| `persona.library.import` | `{ name, text }` | `{ entry }` |
| `persona.library.rename` | `{ id, name }` | `{ entry }` |
| `persona.library.remove` | `{ id }` | `{ removed: true }` |

**UI**：人设弹窗顶部选择来源（不使用/人设库/自定义）；人设库来源显示下拉（名字）、选中项简介与只读全文、导入（粘贴 + 本地文件）、重命名/删除（仅导入项）；自定义来源保留角色名/性格与语气/补充要求与示例；注入预览对两种来源都实时显示 `<dsh_im_persona>` 块。

## 4. 注入点与包裹格式

### 4.1 端到端链路

沿用上下文增强已经在用的入站消息前缀链路（task-3 接入时执行，本阶段只提供纯函数）：

```
渠道受理入站消息
  → 组装 prompt 内容（现有：promptContentForInboundMessage / 纯文本）
  → context enhancement：enhanceContextContent(…)          ← 现有组装点
  → persona：injectPersonaContent(…)                        ← 新增，紧接其后
  → askInWorkspaceSession → HarnessClient.ask → session.prompt（用户消息内容带前缀块）
  → Host agent/pre-step：rewriteInjectedContextMessages(…)
      · 人设块 → 独立 plugin instructions 上下文消息（position: before）
      · source/guidance/reply 块 → 保持现有行为
      · 用户消息只保留用户输入原文
  → 模型看到：plugin 人设上下文行 + source/guidance 行 + 用户消息
```

- 拼接点选择：**不新起系统提示词注入**，复用 `enhanceContextContent` 的同一组装位置；人设块与上下文增强块走同一条前缀链路，语义边界与上游一致。
- Host 没有 Agent loop、或 `harnessBaseUrl` 指向外部 Harness 时，`agent/pre-step` 不会发生：人设块**保留在用户消息内联**，模型仍然能读到（与 guidance 在此场景下的既有行为相同）。
- 注入失败一律回退到原文：`injectPersonaContent` 内部 try/catch，人设问题绝不导致消息投递失败。

### 4.2 拼装顺序

producer 输出顺序（人设在最外层）：

```
<dsh_im_persona>
…已解析人设正文…
</dsh_im_persona>
<dsh_im_source>…</dsh_im_source>
<dsh_im_source_guidance>…</dsh_im_source_guidance>
（引用回复块 / 会话上下文收集块如存在，按既有位置）
用户正文
```

实现方式（task-3 已落地）：

```js
// 现有
content = enhanceContextContent(originalContent, snapshot, sourceFactory);
// 新增：紧随其后 → persona 成为最外层前缀
const persona = capturePersona(this.#persona);
if (persona) {
  content = injectPersonaContent(content ?? text, persona);
  contextEnhanced = true; // 让仅注入人设的媒体消息也走标题清理路径
}
```

`injectPersonaContent` 与 `enhanceContextContent` 同形：字符串 → `${block}\n\n${content}`；数组 → `[{ type: 'text', text: block }, ...content]`；其它类型原样返回。数组场景下人设块是独立 text part，因此不会改写用户正文那一段。

### 4.3 包裹格式：纯文本正文（标签框定）

```
<dsh_im_persona>
你是「大肥鱼」。
性格与语气：……
补充要求：
……
</dsh_im_persona>
```

- 正文是**已解析人设的纯文本**：开标签后、闭标签前各有一个换行；v2 人设库的长 Markdown 原样进入，不做 JSON 字符串化（否则 64k 正文会被转义成一行、模型难以阅读）。
- v1 四字段配置由 `resolvePersonaInjection` 拼成固定格式（角色名/语气/补充要求各一段），与 v2 共用同一注入块。
- 转义：正文中出现的 `<dsh_im_persona>` / `</dsh_im_persona>` 标签字面量替换为 HTML 实体（`&lt;…&gt;`），保证**结束标签只能由拼装器写出**；其它文本（Markdown、HTML、其它 `dsh_im_*` 字样）原样保留。
- 为什么不加 JSON 字段：人设是 owner 自由文本（v2 更是 Markdown 长文），JSON 转义会破坏可读性；块边界由框定换行 + 标签转义保证。
- 正文上限：`PERSONA_TEXT_MAX_LENGTH = 64_000`（与 v2 人设库条目上限一致），v1 内联配置实际约 2.3k。

### 4.4 Host 拆分与配对（task-3 已落地）

`src/channels/shared/injected-context.mjs` 增加一个块类型（共享文件里最小的必要改动）：

- `blockAt` 扫描顺序中 persona 放**第一个**（producer 顺序里它最外层）；
- 识别规则：标签必须成对、开标签后与闭标签前各有一个换行、正文通过 `isPersonaBody`（非空且不超注入上限）——普通用户文本里散落的同名标签（例如 `<dsh_im_persona>x</dsh_im_persona>` 不带框定换行）保持原样，不会成为人设行；
- 产出的 block：`{ position: 'before', form: 'instructions', summary: null, text, value: body }`（`value` 为去掉框定换行的正文，供未来系统提示词去重）；
- `rewriteInjectedContextMessages` 无需改动：它已按 block 生成独立的 `plugin:dsh-im` 上下文消息，并按消息标识与用户消息配对；
- `plugin-src/host/injected-context.mjs` **无需改动**（persona 不需要 registry、不需要 `ownedGuidance` 去重）。

拆分后效果：

| 会话历史 | 内容 |
| --- | --- |
| plugin instructions 行 | 完整 `<dsh_im_persona>…</dsh_im_persona>` 块（独立消息，绑定到这条用户消息） |
| 用户消息 | 用户实际发送的原文（不含人设） |

用户消息保持原样很重要：会话标题（`session-title.mjs` 的 `INJECTED_CONTEXT_PREFIX`）、`/history` 尾部展示（`session-nav-command.mjs` 的同名正则）都只剥离已知前缀块；task-3 已把 persona 段加入这两个正则的最前面，媒体类消息的标题不会把人设正文当标题。

### 4.5 哪些消息注入、哪些不注入

| 入站形态 | 是否注入人设 | 说明 |
| --- | --- | --- |
| 普通私聊/群聊文本消息 | ✅ | 主路径 |
| 带图片/文件的消息、纯媒体消息 | ✅ | 前缀块是独立 text part；不影响附件暂存与 Content 组装 |
| 引用回复消息 | ✅ | 人设块排在引用块之前（人设是外层） |
| 批量输入提交（batch） | ✅ | 它最终也是一次用户回合 |
| `/steer` 补充指令 | ✅ | 进入 Harness 的纠偏文本，与上下文增强对纠偏携带来源的处理一致；注入逻辑在 `control-command.mjs` 的 `steerMessage` 组装点 |
| 其它 `/` 命令（`/new`、`/model`、`/stop`、`/help`、`/history`、`/workspace` 等） | ❌ | 走本地/控制通路，不进入 Harness 的用户回合 |
| 审批回答、提问回答、按钮/交互回执 | ❌ | 有状态交互，不是用户回合 |
| 机器人自己的出站消息、主动投递、状态/错误提示 | ❌ | 不经过入站组装 |

实现约束：命令分支在现有桥接里先从文本解析命令、命中后 `return`，注入代码放在「确定要进入 Harness 回合」之后，天然不会覆盖命令路径；不要在解析前注入。

### 4.6 与上下文增强的关系

| 维度 | 上下文增强 | 人设 |
| --- | --- | --- |
| 作用域 | 群聊/私聊分别配置 | 每机器人一份 |
| 开关 | 分别开关 | 独立开关 |
| 内容 | `<dsh_im_source>` 来源字段（JSON）、`<dsh_im_source_guidance>` 增强提示词 | `<dsh_im_persona>` 身份设定（纯文本 + 标签框定） |
| 组装点 | `enhanceContextContent` | 紧随其后 `injectPersonaContent` |
| 前缀顺序 | 内层（靠后，紧邻用户正文） | 最外层（位于 source/guidance 之前） |
| Host 处理 | source/reply 拆成 context 行；guidance 拆 instruction 行并配合 `dsh-im:source-guidance` 动态上下文 | 拆成 instructions 上下文行（v1）；v2 见 §4.8 |
| 关闭时 | 原样返回 | 原样返回（与 enhancement 同时关闭时内容逐字节不变） |

两者**不共享字段、不相互覆盖、不互相依赖**：只开人设（增强关闭）时只多一个人设块；只开增强时行为与现在完全一致；同时开启时前缀顺序固定为「人设 → 来源 → 增强提示词 → 正文」。不建议把人设塞进增强的 `guidance` 字段：两者的语义（来源使用说明 vs 身份设定）和生命周期（会话范围 vs 机器人范围）不同，混在一起会让关闭增强时连带丢掉人设。

### 4.7 token 成本与上限

- 人设块随每条入站消息进入会话，Host 拆分后每条用户消息对应一条人设上下文行：模型每个回合都会读到它（等于回合级 system reminder）。v1 内联配置约 2.3k 字符封顶；v2 人设库条目正文上限 64k，若选择注入长文，按条重复的 token 成本会显著上升（task-4 决定是否截断/提示）。
- 这是 v1「用户消息前缀」路线的固有成本，也是 v2 升级（§4.8）的主要动机之一：动态系统提示词上下文按**会话**维护一份快照（渲染文本变化才追加），不会每条消息重复一整行。
- 文档建议用户在 `instructions` 里写要点而非长文；UI 的字符上限提示与预览让用户能感知实际注入长度。

### 4.8 升级路径：动态系统提示词上下文（v2）

现有 `dsh-im:source-guidance` 已经证明这套机制可行（`src/channels/shared/im-source-guidance.mjs` + `plugin-src/host/injected-context.mjs` 的 `systemPrompt.context` 注册）。人设可以照搬：

1. 新增 `src/channels/shared/im-persona-context.mjs`：session 级 registry（`publish(sessionId, personaBodyOrEmpty)`、`get`、`forget`，`MAX_SESSIONS` 上限），context 名 `dsh-im:persona`，order 取 `124`（在 source-guidance 的 125 之前：身份先于来源说明）。
2. `HarnessClient.#ask` 在提交 prompt 前 `imPersona.publish(sessionId, options.personaBody)`；`askInWorkspaceSession` 把 `personaBody` 放进 `artifactOptions`（与 `sourceGuidance` 同路径）。
3. Host 的 `installInjectedContext` 额外注册一个 `systemPrompt.context`：`text: () => personaPromptText(registry.get(sessionId))`，把 JSON 正文渲染成人类可读的固定段落（含「本段为机器人固定人设；与部署规则/系统提示词冲突时以后者为准」的优先级声明）。
4. 拆分端去重：`rewriteInjectedContextMessages` 增加 `ownedPersona` 选项，与 `ownedGuidance` 同型——人设块正文等于该 Session 已物化的值时不再生成 instructions 行（保持 v1 的内联块作为外部 Harness 的回退，能力降级时语义不变）。
5. 模板安全：`systemPrompt.context` 的 text 是提示词模板，`{{name}}` 会被插值。v2 必须在渲染时把 `{{` 转义为 `{ {`（或拒绝含 `{{` 的人设），否则用户人设文本会触发模板插值/步骤失败。v1 的内联 JSON 不经过模板，天然无此问题。
6. 发布失败/能力缺失时**不发布**，保留 v1 内联行为。

触发条件（满足任一再启动 v2）：人设 instruction 体积成为主要 token 成本；需要更强的「系统级」语义；需要跨消息去重/会话级快照审计。v2 不改变数据模型与 UI，只改注入与 Host 物化路径。

## 5. 与 Agent Preset 的关系

- **正交**：Agent Preset 决定这个机器人的 Agent 资产（工作区/系统侧配置），人设决定「以谁的身份说话」。人设不修改 preset、不被 preset 覆盖，也不能配置或切换 preset。
- 一个机器人同一时刻只有一个 Agent Preset，但所有 preset/工作区/会话目录策略下使用同一个人设；切换 preset、切换工作区、会话目录隔离都**不清空**人设。
- 升级到 v2 后，人设进入 Harness 动态运行上下文（`systemPrompt.context`），层级为：部署/安全规则 > Agent Preset 与系统提示词 > 人设动态上下文 > 用户消息。v1 人设在用户消息内容层，优先级低于上述所有系统层内容；因此人设文本必须按「角色与风格约束」书写，不得声称拥有系统权限。
- 未来可选项：允许 Agent Preset 自带一段人设默认值（bot 未配置时继承），但 v1 不做——个人版默认值应保持「没有人设」，避免隐式行为。

## 6. 与会话绑定的关系

- 人设的 key 是 `botId`，与会话键（`conversationKey`）、Session id、DS Bot 会话绑定、会话导航环都**无关**；不写 `state.json`，不参与 `withSessionBindingLock`，不触发会话重建。
- 同一机器人所有会话（私聊、群聊、DS Bot 绑定会话、`/go` 切换到的历史会话）读同一个人设。
- 人设保存**不重连机器人、不重建 Session、不清历史**；从下一条进入 Harness 的消息生效，已在 Harness 中/已提交的消息不受影响。
- 保存时机语义（v1）：在 prompt 组装时同步读取 store（`capturePersona`）。因此「已经受理但还没组装 prompt」的消息会用保存后的新人设。如果后续需要更严格的「接收时快照」语义（与上下文增强一致），可在渠道的 accepted-message 生命周期里加一张 persona 快照 map（接入清单 §13.3 列为可选项，不是 v1 必需）。
- v1 的人设上下文行会写进会话历史；修改或关闭人设**不回收**已经写入的历史（与上下文增强的隐私说明一致），下一条消息起才停止新增。

## 7. 命令系统结论

明确结论（task-3 照此实现）：

| 问题 | 结论 |
| --- | --- |
| 命令是否注入人设 | **不注入**。所有 `/` 命令、审批/提问回答、交互回执走控制通路，不是进入 Harness 的用户回合。唯一例外是 `/steer` 的补充指令文本：它是进入 Harness 的纠偏指令，注入人设（与上下文增强对纠偏携带来源的处理一致）。 |
| `/new` 后是否保留人设 | **保留**。人设按 bot 存储，不属于会话状态；`/new`、`/reset`、`/clear`、切换工作区/Agent Preset/会话目录都不改变人设。新会话第一条消息即按当前人设注入。 |
| 多人设切换命令 `/persona` | **v1 不提供**（见下方理由）；v2 候选方案见下。 |
| 是否新增命令/帮助文案 | **否**。不加命令目录、帮助、权限映射与三语文案，减少与渠道裁剪/品牌改造的冲突面。 |

`/persona` 不在 v1 的理由：

1. **权限边界**：个人版唯一的信任根是 owner（能打开 DSH 设置页/调用管理 RPC 的人）。群聊里任何成员都能发命令，现有 `access-policy` 只表达「能否与机器人对话」，无法安全表达「谁能改机器人人设」；把配置写入权限暴露给群成员会突破当前边界。
2. **配置 vs 操作**：人设是低频配置，不是会话级操作；用设置页保存有校验、预览、错误提示与原子写入，命令通道要复刻这些成本很高。
3. **成本与冲突**：新增命令要同步 `command-catalog.mjs`、命令帮助、`command-permission.mjs`、三语 i18n、渠道菜单/命令注册（微信、QQ 各一套），在裁剪与品牌改造并行期风险大、收益低。

v2 候选设计（若届时需要）：`/persona`（无参数）= 只读展示当前角色名/启用状态；`/persona <name|id>` = 在 owner 于 UI 预先配置的多套人设间切换。仅对 owner 生效（私聊 owner，或 access policy 判定的 owner 身份），并在命令目录中登记独立权限级别。数据模型预留扩展：`personas.json` 记录内可增加 `profiles`/`active` 字段并升 version。

## 8. UI 页签与交互

### 8.1 位置与入口

- 放置位置：机器人设置卡片内、**上下文增强之后**的纵向区块（`WorkspaceEditor → ModelEditor → AgentPresetEditor → ContextEnhancementEditor → PersonaEditor`）。裁剪后只剩微信、QQ 两个渠道设置页，各挂一次；若裁剪/品牌改造后 QQ 还保留额外的 Token 接入卡片，同一卡片列表里再挂一次即可（组件与宿主容器无关）。
- 交互形态采用既有机器人设置项的「一行入口 + 弹窗」模式（与上下文增强完全一致），而**不是**顶层页签条：`bot-settings-tabs.js` 是 DSH「投递设置」页内部的页签条，机器人卡片里的设置项都是纵向区块。`PersonaEditor` 不依赖宿主容器，若 Lead 以后希望改成页签/独立面板，直接把它作为面板内容挂载即可，组件无需改动。
- 入口行：人设图标 +「人设」+ 状态标签（`未启用` / `已启用`，`data-active` 控制高亮）+ 展开箭头；`aria-haspopup="dialog"`。
- 与机器人别名的区分：别名（`bot-alias.mjs`）改的是**设置页显示名称**；角色名 `name` 只进入模型提示词，两者互不覆盖。UI 的帮助文案明确这一点。

### 8.2 交互状态机

| 状态 | 行为 |
| --- | --- |
| 卡片加载 | `persona` 来自渠道状态快照（task-3 在 status 的 `bots[]` 增加 `persona` 字段）；缺失/损坏按默认值显示「未启用」 |
| 打开弹窗 | 以当前快照初始化草稿；挂载期间外层状态刷新不覆盖未保存编辑（与上下文增强一致） |
| 编辑 | 开关、角色名（input，maxLength=40）、性格与语气（textarea，240，示例/清空）、补充要求（textarea，2000，示例/清空）；任意编辑清除错误 |
| 空内容 | `enabled` 且内容全空时显示提示「保存后不会注入」；仍允许保存（等价未启用），避免用户被迫二选一 |
| 注入预览 | 只读 textarea 实时显示 `personaBlock(draft)`；空内容时显示提示文案。用 `value` 渲染，**不经过** React 文本节点，避免用户人设被设置页动态翻译规则改写 |
| 保存 | `validatePersona(draft)` → `onSave`（`bot.persona.set`）→ 成功后关闭并回焦入口；保存中禁用全部控件并显示「保存中…」 |
| 失败 | 弹窗保留草稿，`role="alert"` 展示错误（校验错误原文；网络/存储错误用兜底文案）；保存失败不关闭 |
| 关闭 | 取消、Esc、点击遮罩均可关闭（保存中不可关）；关闭时恢复入口焦点 |
| 禁用 | 机器人连接操作进行中（`busy`）时整个入口与弹窗禁用，避免保存与重连并发 |

### 8.3 样式与无障碍

- 结构样式复用现有 `dim-context*` 类（入口、弹窗、header、tooltip、footer、错误行）；额外挂 `dim-persona*` 类（`dim-personaEntry/Backdrop/Dialog/Header/Body/Field/Control/Input/Preview/Hint/Status/SwitchRow`）便于后续单独精修。task-3 在 `plugin-src/client/styles.js` 只需补最少几条：`dim-personaInput` 的宽度/字体、`dim-personaPreview` 的等宽字体与高度、`dim-personaHint` 的弱化字号；**不加也能用**（复用 context 样式即可）。
- 无障碍：`role="dialog"` + `aria-modal` + `aria-labelledby/describedby`；打开聚焦弹窗、Tab 循环、Esc 关闭、关闭回焦；帮助按钮 `aria-label` + tooltip；状态标签 `aria-live="polite"`；预览 textarea 有 `aria-label`。

## 9. i18n（中/英/俄）

### 9.1 机制与品牌化

- 设置 UI 使用 `plugin-src/client/i18n.js` 的 `h` / `localizeText`：数据源是**中文源文案**，`h()` 自动翻译字符串子节点与 `aria-label/placeholder/title` 等属性；字段值（用户输入、预览 `value`）不参与翻译。
- `persona-settings.js` **不硬编码 i18n 命名空间或品牌串**：只从 `./i18n.js` 导入 `h`、`localizeText`。品牌改造把命名空间从 `dsh-im` 改为 `dsh-im-persona` 时，本组件零改动，只需把下表键并入同一份词典。
- Host 侧错误文案（`persona.mjs` 校验、`persona-rpc.mjs` RPC 错误）由管理 RPC 原样到达设置页，由组件用 `localizeText(...)` 展示；因此**只需要加到客户端词典**，不必在 Host 词典重复维护（这些文案不会作为机器人聊天消息发出）。若 RPC 错误来自 Host 统一生成的兜底句子（如网络层），沿用现有动态规则。
- 词典落地位置（task-3）：`plugin-src/client/i18n.js` 的 `EN` 对象（含 `COMPOSED`）与 `plugin-src/client/i18n-ru.js` 的 `RU` 对象。键必须是逐字节一致的中文源文案（含 `\n` 与 `<dsh_im_persona>` 等标签字面量）。

## 10. 安全边界

### 10.1 人设属于用户消息内容，还是系统提示词？

**v1 明确选择：用户消息内容。** 理由与取舍：

| 维度 | 用户消息内容（v1 采用） | 系统提示词（v2 升级） |
| --- | --- | --- |
| 语义层级 | 低于系统提示词/Agent Preset/部署规则；模型仍会遵循角色要求，但系统层冲突时以系统层为准 | 进入 Harness 动态运行上下文，更接近「常驻指令」，语义更强 |
| 能力降级 | 外部 Harness、无 Agent loop 时也生效（内联在消息里） | 依赖 `systemPrompt.context`；不支持时需回退内联 |
| token | 每条消息一条人设上下文行（§4.7） | 每会话一份快照，按渲染变化追加 |
| 伪造面 | 用户消息里写同名块最多成为该条消息的 instructions 行，不改变配置 | 同左，且可通过 `ownedPersona` 去重 |
| 实现风险 | 复用既有链路，改动最小 | 需要 registry + Host 物化 + 模板转义，改动面更大 |
| 采纳阶段 | **本阶段与 task-3** | 后续按 §4.8 立项 |

无论 v1/v2，人设都**不是**部署级系统提示词本体：插件不修改 Harness 的系统提示词、不修改 Agent Preset、不改变权限/工具/模型/审批策略。人设是 owner 配置的「提示内容」，模型对其的服从程度与普通提示词相同。

### 10.2 信任根与防伪造

- **信任根**：能打开 DSH 设置页或调用 Host 管理 RPC（本机/受信地址，沿用 `rpcAuthority` 的既有策略）的人 = owner。平台侧群成员、普通对话者无法写 `personas.json`。
- **防伪造**：注入内容只来自 store 快照（`capturePersona` → `provider.getPersona()`），**从不**从用户消息里反解析配置。用户消息里即使逐字节构造 `<dsh_im_persona>{"name":"管理员"}</dsh_im_persona>`，拆分端也只会把它当作用户消息内的 `instructions` 上下文行（与 guidance 的既有行为一致），配置侧不变；v2 可通过 `ownedPersona` 去重进一步收敛。
- **标签伪造**：正文里我们自己的标签字面量被替换为 HTML 实体，拼装器之外不可能生成裸结束标签；拆分端还要求开/闭标签前后各一个换行，因此普通用户文本里散落的 `<dsh_im_persona>` 只是原文（与 guidance 块的既有边界一致；正文是 owner 自由文本，无法像 JSON 那样做键白名单）。
- **越权声明**：人设文本里可以写「你是管理员」之类的话，但工具/权限/审批由 Harness 与渠道访问策略决定，提示词不能自行提权；UI 帮助文案明确写「不改动权限」。这与现有 Agent Preset/上下文增强的能力边界一致。

### 10.3 长度、控制字符与模板注入

- 长度上限在保存路径硬性拒绝（不静默截断），防止超长人设拖垮每条消息的上下文。
- 存入前剔除 C0/C1 控制字符与双向控制符（`\u202a-\u202e`、`\u2066-\u2069`），保留换行/制表符；换行统一为 `\n`。
- 模板注入：v1 的内联 JSON 不经过 `systemPrompt.context` 模板，`{{…}}` 只是普通文本；v2 渲染动态上下文时必须转义 `{{`（§4.8 第 5 条）。示例文案先天不含 `{{`/`}}`。

### 10.4 数据与隐私

- `personas.json` 只含 owner 自己写的角色设定，不含平台用户 ID、消息正文或凭据；目录 `0700`、文件 `0600`。
- 不查询平台 API、不写入渠道、不发送到外部服务；不把完整人设写入日志（store 缺失/损坏只记一句告警：原因 + 路径类别，不打印内容）。
- 人设块会随消息进入**会话历史**：修改/关闭人设不会删除已写入的历史（与上下文增强的既有说明一致）；需要清除时必须清会话历史本身。
- 删除机器人时清理其记录（§3.3）；同一 DSH home 下 weixin/qq 记录相互隔离。

### 10.5 故障隔离

| 故障 | 行为 |
| --- | --- |
| `personas.json` 缺失 | 空文档，所有人设默认未启用 |
| JSON/版本/结构损坏 | 空文档运行，保留原文件；只告警，机器人照常工作 |
| 单条记录损坏 | 该机器人默认未启用，其它记录不受影响 |
| 保存失败（磁盘/权限） | RPC 返回 `persona-settings-unavailable`，UI 显示兜底文案；内存快照保持旧值 |
| 注入函数抛错 | `injectPersonaContent` 内部兜底，返回原始内容继续投递 |
| Host 拆分失败 | Host 既有 try/catch：块保留内联，用户消息不丢 |
| 人设为空/关闭 | 零拼装、零字段读取，消息逐字节不变 |

## 11. RPC 方法清单

### 11.1 端点

`plugin-src/host/persona-rpc.mjs` 通过 `registerManagementRpc` 注册**独立 Host 管理通道**：

- 通道常量：`PERSONA_RPC_CHANNEL = '/persona'`（定义在 `persona.mjs`，Host 与 client 共用）
- 实际 HTTP 路径：`/api/dsh-im/persona`（`management-rpc.mjs` 的 `dsh-im` 前缀 + 通道名；品牌前缀只由该模块决定，本模块不复述品牌串）
- 使用方式与 `channel-list-rpc.mjs` 相同：`installPersonaRpc(ctx, { authority, config })` → 返回清理函数；在 `ctx.connection.fetch` 就绪后安装（task-3 放入 `plugin-src/host/index.mjs` 的同一段 try/catch 安装区）。

| method | 载荷 | 成功返回 | 失败返回 |
| --- | --- | --- | --- |
| `bot.persona.get` | `{ botId }` | `{ ok: true, value: { persona } }`（未配置返回默认人设，不是错误） | `bad-request` / `cancelled` / `persona-settings-unavailable` |
| `bot.persona.set` | `{ botId, persona: { enabled, name, tone, instructions } }` | `{ ok: true, value: { persona } }`（返回归一化后的配置） | `bad-request` / `cancelled` / `persona-settings-unavailable` |

### 11.2 校验与错误码

- `botId`：`^[A-Za-z0-9_-]{1,128}$`；只接受表中字段，多余/缺失字段一律 `bad-request`；未知 method 也 `bad-request`。
- `persona`：与 `validatePersona` 同一套规则（四字段、类型、长度、控制字符归一化）。
- 错误码：
  - `bad-request`：载荷/字段/长度不合法，消息可直接展示；
  - `cancelled`：请求被取消（`signal.aborted`）；
  - `persona-settings-unavailable`：读写 store 失败，不暴露磁盘细节。

### 11.3 客户端调用与状态快照

- 设置页通过 `callManagementRpc(connection, PERSONA_RPC_CHANNEL, method, payload, signal)` 调用（与其它管理通道一致）；`PERSONA_ENDPOINTS` 提供 `bot.persona.get/set` 字面量。
- 机器人卡片初始值来自渠道状态快照：task-3 在微信/QQ 的 `status().bots[]` 上增加只读 `persona` 字段（由渠道 production 用同一个 store 单例同步装饰，见 §13.1）。**不新增 list 端点**：每卡按 botId 已经有状态字段，避免 N+1 RPC。
- 保存成功后用 `set` 返回值更新本地快照（无需重读 status）；`get` 主要用于状态字段缺失时的兜底/诊断。
