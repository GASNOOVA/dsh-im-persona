## 1. 一句话结果

每个机器人可在设置页配置/启用「人设」；启用后，微信与 QQ 的每条进入 Harness 的用户消息都会带 `<dsh_im_persona>` 前缀块，Host `agent/pre-step` 把它拆成独立的 `instructions` 上下文行，用户消息保持原文。命令、审批与提问回答不注入；`/steer` 的补充指令注入；`/new` 保留人设。人设按 `botId` 持久化在 `<DSH_HOME>/integrations/dsh-im/personas.json`。

## 2. 设计偏差（为 task-4 零返工，已与 Lead 的新需求对齐）

Lead 在 task-3 执行期间提出 task-4（内置大肥鱼人设 + 人设库），要求渠道侧只依赖「已解析人设结果」接口。据此在 task-3 内提前做了两处重构（`02-人设能力.md` §3.7/§4.3 已同步更新）：

1. **已解析人设接口**：渠道 provider 返回 `{ enabled: true, name, text } | null`，渠道只调用 `capturePersona(provider)` + `injectPersonaContent(content, resolved)`，不读取 v1 四字段、也不知道人设库/存储结构。
   - `persona.mjs` 新增 `resolvePersonaInjection(value)`：v2 已解析结果原样采用 `text`；v1 四字段配置拼成固定可读正文（角色名/语气/补充要求），两者共用同一注入块；新增 `isResolvedPersona`、`PERSONA_TEXT_MAX_LENGTH = 64_000`、`RESOLVED_PERSONA_FIELDS`。
   - host production 的 provider 改为 `getPersona: () => resolvePersonaInjection(personas.personaFor(botId))`；task-4 只需替换这一处解析器（人设库感知版本），渠道接线与拆分逻辑不变。
2. **注入块改为纯文本 + 标签框定**（原设计是 JSON 正文）：
   - 格式：`<dsh_im_persona>\n<正文>\n</dsh_im_persona>`；
   - 理由：v2 人设库正文是 owner 自由文本（内置大肥鱼的长 Markdown，上限 64k），JSON 字符串化会把换行转义成一行、模型不可读；
   - 安全：正文中出现 `<dsh_im_persona>`/`</dsh_im_persona>` 标签字面量替换为 HTML 实体，结束标签只能由拼装器写出；拆分端要求「成对标签 + 开标签后/闭标签前各一个换行 + 非空正文」，普通用户消息里散落的同名标签保持原文；
   - v1 内联配置的文本由 `resolvePersonaInjection` 生成，模型可分辨角色名/语气/补充要求。
